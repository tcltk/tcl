polyhedra.tcl: plain Tcl and TIP 759

The rotating polyhedra demo by Gerard Sookahet (2005), on the left as it was, and on the right with its maths written with the syntax of TIP 759. It takes up, proc by proc, the comparison made for Calc; the switch shows the Calc version in the right column instead, with the same left column.

TIP 759 features used: [( … )] expression substitution, native lists (a, b, c), TIP 282 assignments x = …;, expression scripts {( … )} as the body of proc, foreach…, tuple assignments (x, y, z) = $V;, and raw commands, without brackets, for the commands the expression parser knows (global scx scy vdist;, n = llength $lcoords;, lindex $M1 $i 0 * lindex $M2 0 $j); the procs of the demo keep their brackets. And user operators: a proc tcl::mathop::crossProd is used as $U \crossProd $V, with the precedence of *. Everything is parsed by Tcl and compiled with the proc: nothing to transform afterwards.

The columns TIP 759, operators in tcllib count the demo as it would be if the ten operators came from math::linearalgebra (see below the speed table): the definitions of \crossProd, \matrixProd, \matrixVectorProd, \project and the vector operators leave the file, and one package require line takes their place. Characters are counted with the white space the syntax needs, and only that: one blank between two words of a command (set a 1 counts 7), none for indentation, none around an operator in an expression ($X + $x counts as $X+$x), and one character for a line end that ends a command. Comments count, with one blank between words, and their line end. To check these rules, the code of each column was rewritten in this minimal form and run: the original, Calc (with its colon package) and TIP 759 give the same results as before. The Calc column of DisplayModel includes two changes that are not about the maths.

The product of matrices is three times faster: lmap goes over the values, where the original updates each cell by index with lset in three loops. MatrixRotation, which calls it twice, gains as much.

The rest of the TIP 759 code is written with vector operators, as in a textbook: the cross product is the axial vector of the antisymmetric part of a tensor product, a matrix is transposed into column vectors for dot products. This is the most readable form, and here the slowest, but the cause is not the syntax: the operators are procs, and a proc call costs about a microsecond, several per operation, where the original wrote the arithmetic inline. The last two columns measure the same TIP 759 code with five operators written in C (\add, \sub, \dot, \crossProd and \transpose, a prototype of about 80 lines loaded as an extension into tcl::mathop; nothing else changes): most procs are then as fast as the original or faster, and a frame of the animation (Transformations, then Intensity) takes 47 µs for a cube, against 79 µs with the original, and 87 µs with the operators as procs. Barycenter and Projection stay a little slower than the original, mostly because lmap and the operators build a new list for each point. A geometry library compiled in C, on a compact representation of vectors of numbers, would remove that too.

Where the operators would live. None of these operators is specific to the demo: \add, \sub, \dot, \transpose, \tensorProd, \axial, \crossProd, \matrixProd, \matrixVectorProd, and even \project, are the common vocabulary of linear algebra and 3D graphics. Their definitions could be provided by the Tcl library math::linearalgebra of tcllib, as procs of tcl::mathop, possibly compiled in C. A single line, package require math::linearalgebra, would then define them all beforehand: the "Vector operators" section would shrink to that line, and the code of the demo would run at the speed of the C column.
